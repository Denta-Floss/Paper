# Constrained-network results — November 2026

Generated by `backend/test/benchmarks/network-throttle.js` on 2026-11-20; 50 runs per scenario (10 for the August model).

## Conditions of this run

Measured on the development Mac while an Android emulator (≈380% CPU) and a video application (≈100%) were also running: load average ≈16–17 on 12 cores. Earlier 10- and 20-run passes of the same benchmark on the same code, at heavier contention, measured `/api/items` at 41 ms total and 33 ms in SQLite at p99, and `/api/inventory/overview` at 29 ms in SQLite — over the 25 ms SLO — while a repeat 20-run pass right after this one measured 14 ms and 9 ms. The network results barely move with load (they are the link's); **the server-time results do**, and the items list is the one closest to the limit on a busy machine: its cost is the Node SQLite driver turning ~1,600 rows into objects for 300 parts, and it grows with the catalogue. Re-run on the production host before quoting server time as a guarantee.

What changed on the server to get here, found by this benchmark: the items list read its relations seven queries per part (now one per table for the whole list); the challan list five per challan (now one per kind); `order_items`, `delivery_challan_items` and `order_material_requirements` had no index on `item_id`, so each part's usage count scanned all three; `item_variation_nodes` had no index on `item_id` at all, so opening one part scanned every node of every part. Items list server time went 444 → 13 ms at p50, challans 96 → 3 ms.

*Total* is time to first byte with nothing in between: SQLite and the JavaScript that builds the answer. *In SQLite* is the server's own `Server-Timing: db` (kernel/db-timing.js, on with `PAPER_DB_TIMING=1`): the time the request held the database, which every other request — writes included — waits behind. The SLO is asserted on that. A request whose total is over 25 ms spends the rest in JavaScript building a large answer; it occupies the CPU, not the database.

## How the link is modelled

A TCP proxy in front of the server (`backend/test/benchmarks/throttle-proxy.js`): one queue per direction drained at the link's bandwidth and shared by every connection; half the round trip each way; one round trip of handshake per new connection; slow start from a 10-segment window doubling each round trip; 2% loss modelled per 1448-byte segment as a resend one round trip later that holds up what follows it on that connection. Not modelled: the real TCP stack (the proxy speaks loopback), congestion-window collapse after loss, jitter. Each run starts on fresh connections, as a launch does; the list scenarios reuse one already open, as a refresh inside a session does. The client sends `Accept-Encoding: gzip`, as the apps do (the August model sends `identity`).

The workspace: the demo seed filled through the API to 300 parts, 250 order lines, 150 challans, 120 materials, 40 clients, 15 vendors, 60 dies and 25 machines (`backend/test/helpers/sized-workspace.js`).
